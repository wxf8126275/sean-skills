# Design: Artifact Catalog（产物目录与需求关联）

> Generated: 2026-10-12
> Status: APPROVED

## 1. 问题

`sean run` 执行过程中产生的**非代码产物**（数据库迁移脚本、批处理命令、配置模板）当前不在 plan 的 `files_create` 里，导致：

| 问题 | 后果 |
|------|------|
| `sean undo` 恢复不了 | 回滚时产物残留，状态不一致 |
| `sean sync` 看不到 | 上下文丢失后无法恢复 |
| `handoff.md` 不记录 | 下一个 AI 不知道有这些文件 |
| `sean learn` 扫不到 | 无法从历史产物提取模式 |
| 需求文档不包含 | 需求与产物分离，知识链断裂 |

## 2. 关键决策：两类产物分开处理

| | A. 可执行产物 | B. 记录型产物 |
|---|---|---|
| 例子 | DB 迁移脚本、批处理命令、配置模板 | 需求、plan、测试报告、交接文档 |
| 消费者 | 项目运行时 / CI / 人手动执行 | AI / 人（阅读理解） |
| 项目是否期待它在标准位置 | ✅ 期待（`migrations/`、`scripts/`、`config/`） | ❌ 无所谓 |
| 归需求目录 | ❌ **破坏项目** | ✅ 天然合理 |

**结论**：A 类产物必须留在项目标准位置；B 类产物天然属于 `docs/`。

**反例（已否决）**：把 `migrations/001_create_users.sql` 移进 `docs/artifacts/<feature>/migrations/`

理由：
1. 破坏项目自身约定 —— alembic / Flyway / Django migrations 都去 `migrations/` 找
2. 运行时找不到 —— 启动脚本、CI、部署流程按标准路径找
3. 违背 `AGENTS.md` —— 项目规范说放哪就放哪
4. `sean undo` 语义混乱 —— 删迁移脚本 ≠ 回滚数据库状态

SKILL.md:160 已明确：`Database: schema, migration, entity` 是应用架构的一层，不是文档。

## 3. 方案：产物目录 = 索引，不是容器

### 3.1 目录结构

```
<project>/
├── migrations/001_create_users.sql      ← 产物在应用标准位置（不变）
├── scripts/init_admin.sh                ← 产物在应用标准位置（不变）
├── config/jwt.template
└── docs/
    ├── requirements/2026-09-29-auth.md
    ├── plans/2026-09-29-auth.md
    ├── artifacts/2026-09-29-auth.md     ← 新增：产物目录（只放索引）
    └── test-reports/2026-09-29-auth/
```

### 3.2 `docs/artifacts/<date>-<name>.md` 格式

```markdown
# Artifacts: <Feature Name>

> Requirement: ../requirements/<date>-<name>.md
> Plan: ../plans/<date>-<name>.md
> Generated: <ISO8601>

## Database

| Path | Type | Task | Purpose | Status | Executed | Verified |
|------|------|------|---------|--------|----------|----------|
| `migrations/001_create_users.sql` | database | 1 | 用户表结构 | created | ✅ | ✅ |
| `migrations/002_add_indexes.sql` | database | 1 | 索引 | created | ⬜ | ✅ |

## Batch

| Path | Type | Task | Purpose | Status | Executed |
|------|------|------|---------|--------|----------|
| `scripts/init_admin.sh` | batch | 1 | 初始化管理员账号 | created | ⬜ |

## Config

| Path | Type | Task | Purpose | Status | Executed |
|------|------|------|---------|--------|----------|
| `config/jwt.template` | config | 2 | JWT 密钥配置模板 | created | ⬜ |

## Execution Log

- 2026-09-29 14:32 `migrations/001_create_users.sql` → applied (3 tables)
- 2026-09-29 14:33 `scripts/init_admin.sh` → 1 row inserted
```

`Executed` 与 `Verified` 分离：脚本被创建 ≠ 脚本被真实执行过。这是两个独立事实。

### 3.3 产物文件头部反向引用

```sql
-- migrations/001_create_users.sql
-- Requirement: auth-feature (docs/requirements/2026-09-29-auth.md)
-- Task: 1 (db-schema)
-- Generated by: sean run
-- Catalog: docs/artifacts/2026-09-29-auth.md

CREATE TABLE users (...);
```

```bash
#!/bin/bash
# scripts/init_admin.sh
# Requirement: auth-feature (docs/requirements/2026-09-29-auth.md)
# Task: 1 (db-schema)
# Generated by: sean run
# Catalog: docs/artifacts/2026-09-29-auth.md
```

## 4. 三层追溯

| 方向 | 机制 | 载体 |
|------|------|------|
| 需求 → 产物 | `requirements/*.md` 的 `Artifacts (expected)` 段声明期望类型 | 需求文档 |
| 产物 → 需求 | 文件头注释 + `docs/artifacts/*.md` 索引 | 产物文件 + catalog |
| 机器可读 | `state.json` 的 `artifacts[].requirement_ref` | state.json |

## 5. 需求文档的 Artifacts (expected) 段

```markdown
## Artifacts (expected)

- **Database**: 用户表结构（建表 SQL）
- **Batch**: 管理员账号初始化脚本
- **Config**: JWT 密钥配置模板

> 需求文档只声明**需要什么类型**，不声明具体路径。具体路径由 `sean plan` 决定。
```

**由谁写**：用户手写，或 AI 在 `sean start` 时推断后用户确认。

理由：需求文档是**契约**，产出什么应该由需求方定，不是实现方。

## 6. Plan 的 task artifacts 字段

```markdown
### Task 1: db-schema
- **Creates**: `src/db/schema.py`
- **Artifacts**:
  - `migrations/001_create_users.sql` (database, schema)
  - `scripts/init_admin.sh` (batch, 初始化管理员账号)
- **Modifies**: —
- **Test**: `tests/test_schema.py`
- **Acceptance**: Schema creates table with correct columns
```

## 7. State Schema 扩展

```jsonc
"tasks": [
  {
    "id": 1,
    "name": "db-schema",
    "artifacts": [
      {
        "path": "migrations/001_create_users.sql",
        "type": "database",
        "purpose": "用户表结构",
        "requirement_ref": "auth-feature",
        "catalog": "docs/artifacts/2026-09-29-auth.md",
        "status": "created",
        "executed": false,
        "verified": false
      }
    ]
  }
]
```

`status` 枚举：`declared | created | failed`
`executed` / `verified`：布尔，独立于 status

## 8. 命令改动

| 命令 | 改动 |
|------|------|
| `sean start` | 需求文档模板增加 `Artifacts (expected)` 段；可选询问是否产生非代码产物 |
| `sean plan` | task 模板增加 `artifacts` 字段；从需求的 expected 推导具体路径 |
| `sean run` | task 执行时按 `artifacts` 创建文件；生成 catalog；文件头加反向引用；记录 `executed`/`verified` |
| `sean undo` | 回滚时同时删除 `artifacts` 声明的文件；catalog 标记移除 |
| `sean sync` | 从 catalog + state.json 恢复产物索引 |
| `sean handoff` | handoff.md 增加 Artifacts 段 |
| `sean learn` | 扫描 `docs/artifacts/` 提取模式 |
| `sean bug` | bug 修复若产生新产物，一并记入 catalog |

## 9. 收益

1. 不破坏项目 —— 产物在应用该在的位置
2. 可追溯 —— 任何产物都能查到属于哪个需求/任务
3. `sean undo` 可回滚 —— 按 state.json 精确删除
4. `sean sync` 可恢复 —— 从 catalog 重建索引
5. `handoff.md` 可交接 —— 完整产物清单
6. `sean learn` 可学习 —— 扫描 catalog 提取模式

## 10. 验收标准

- [ ] 模板：requirement / plan 增加 Artifacts 段
- [ ] `sean plan` 能在 task 里声明 `artifacts`
- [ ] `sean run` 能创建产物文件 + 生成 catalog + 写文件头注释
- [ ] `sean undo` 能删除产物文件
- [ ] `sean handoff` 输出 Artifacts 段
- [ ] 端到端：跑一个含迁移脚本的示例 feature，验证 catalog 与 state.json 一致
